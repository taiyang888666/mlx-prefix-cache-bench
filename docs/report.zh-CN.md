# SGLang MLX 四路并发优化实测

2026 年 11 月 21 日 · Apple Silicon

## 首段文本为何变慢

上一轮对长上下文分支优化了词表投影和 KV 布局。四路并发压测出现首段文本中位延迟回退。拆开两部分复测后，首段文本中位数回退随 KV 布局优化出现。原版两轮合并的首段文本 P50 为 122.2 ms，词表优化为 121.5 ms，单独使用 KV 布局优化为 152.8 ms，两个优化组合为 143.3 ms。

调度器在同一批接收三个热缓存请求时，每个请求约 2,401 个输入 token，其中 2,389–2,390 个已命中，只需补算 11–12 个 token。下表按批次汇总。排队一栏先取每批请求的中位数，再跨批次取中位数。

| 模式 | 三请求批次 | 排队 | 准备并提交 MLX 计算图 |
| --- | ---: | ---: | ---: |
| 原版 SGLang | 3 | 5.76 ms | 86.72 ms |
| 词表投影优化 | 4 | 5.52 ms | 86.11 ms |
| KV 布局优化 | 2 | 8.63 ms | 96.94 ms |
| 两者组合 | 2 | 6.38 ms | 98.16 ms |

主要差距出现在首个 token 的准备和提交阶段，排队增幅小得多。计时跨度包含 `mx.async_eval` 调用，属于服务进程墙钟时间。采样未拆到各个 Metal 算子的执行时间。

将几个请求合成一次前向计算的试跑改写了其中一条回复，从 `21 days.`（5 token）变成 `21`（3 token）。该变体的差异和时延记录见 `group-smoke.json`，候选补丁保留逐请求前向计算。

在缓存优化候选中，长前缀命中且只需补算少量 token 时，直接保留模型前向已产生的 K/V 张量。首个 token 返回前省去扩容缓冲区的拷贝。后续解码第一次写入时把已有缓存、新 KV 和预留空间合成一次追加操作。逐请求的模型前向和缓存槽分配保持一致。

## 测试环境与指标

- SGLang v0.5.23 MLX 后端，提交 `297e54fd105e974cdf401e5b4d20253a22c16f90`。Apple M4 Pro，24 GiB 统一内存。Python 3.12.13、MLX 0.32.4、MLX-LM 0.32.2、PyTorch 2.13.0、Transformers 5.19.0。
- 固定 `mlx-community/Qwen3-0.6B-4bit` 修订 `73e3e38d981303bc594367cd910ea6eb48349da8`。双方使用同一模型权重，`model.safetensors` 的 SHA-256 为 `392e8d466d56100ada00eb82031fb854297fc9e389b7d303eba3af114e87bce2`。
- 四路组配置 8,192 个可用 BF16 KV 槽加一个填充槽，池大小 939,638,784 字节（896.11 MiB），MLX 内存分配指导值 6,144 MiB。常规串行组使用 3,072 个可用 KV 槽加一个填充槽，池大小 352,436,224 字节（336.11 MiB），MLX 指导值 3,072 MiB。长对话组使用 896.11 MiB 池和 4,096 MiB 指导值。各组两端的配置成对一致，分配器复用缓存上限设为 256 MiB。
- 每轮按对照与候选交替顺序启动独立服务进程，只使用本机 HTTP 服务。每种负载计时前清理前缀缓存和预热。四路并发每个进程预热长文档后通过四个客户端处理 12 条分支，测量整个并发波次的墙钟完成时间。串行按请求计时求和。首段文本度量第一段可见文本到达客户端的时间。
- 输出上限 12 token，使用贪心解码。逐条比对回复、输入和输出 token 数；串行还核对前缀命中 token 数。并发请求谁先进入调度可能变化，原始记录保留各请求的缓存命中数。
- 指导值按运行中记录的 MLX 活跃分配峰值复核，范围为进程内 MLX 统计。曾尝试每个进程跑两波并发，原版 SGLang 的峰值越过 6,144 MiB，保留日志并采用独立进程跑单波的方案，保持共同预算。

## 正式四路并发

合并写入模式在同批中先分别运行各请求，读取已有前缀。随后按层把各请求的新 K/V 合并写入彼此独立的槽位。长前缀相同和不同的请求均从各自槽位读取。合并写入适用于至少两个长前缀已命中、尾部短且结束预填充的 Qwen3 请求。调度器发现其他请求在等待或在解码时，先放行的单个请求也可以使用紧凑 KV。串行仍使用上一轮的词表和 KV 布局优化，常规长输入沿用原路径。

合并写入模式的整批中位耗时从 718.0 ms 降至 640.8 ms，各轮配对降幅中位数为 **10.7%**。整批时间 4/4 轮胜出，首段文本 P50 和 P95 分别 4/4 和 4/4 轮胜出。合并各轮请求后，P50 为 120.2 → 92.9 ms，P95 为 160.9 → 110.6 ms。实测最高峰值为 5,676.0 → 5,170.2 MiB。

单独启用紧凑缓存时，并发 P50 和 P95 分别改善 6/6 和 6/6 轮，整批耗时只改善 1/6 轮。该模式最高峰值为 4,379.7 MiB。随后加入合并写入，允许单请求走紧凑 KV 的试验版整批胜出 6/6 轮，配对降幅中位数 11.2%，但在第一轮串行对照中出现回退。保留这一轮及后续中止前的日志。随后将紧凑 KV 和合并写入限定在符合条件的多请求批次。该版本保住了串行提速，四路并发整批耗时胜出 3/4 轮。交付版本用调度器的等待和解码状态识别并发中的单请求，并独立复测。

## 分支和连续对话回归

| 负载 | 原版 → 候选整批中位 | 各轮配对降幅中位数 | 合并各轮首段文本 P95 | 整批胜出 |
| --- | ---: | ---: | ---: | ---: |
| 长文档分支 | 1137.8 → 875.8 ms | 23.0% | 323.9 → 248.8 ms | 2/2 |
| 连续增长的上下文 | 588.0 → 454.0 ms | 22.8% | 143.6 → 109.4 ms | 2/2 |
| 热点与一次性长请求交错 | 2691.8 → 2069.5 ms | 23.1% | 335.1 → 258.8 ms | 2/2 |
| 冷请求 | 2716.4 → 2105.8 ms | 22.5% | 328.9 → 257.8 ms | 2/2 |
| 多消息对话分支 | 1269.8 → 1185.3 ms | 6.6% | 683.2 → 645.4 ms | 3/3 |
| 带回真实助手回复的连续对话 | 1329.7 → 1233.5 ms | 7.2% | 662.3 → 814.9 ms | 2/3 |

常规串行组峰值原版 2,546.2 MiB，新版本 1,751.4 MiB。长对话组峰值原版 3,265.9 MiB，新版本 2,628.5 MiB。上一轮相同常规负载的分支和连续增长上下文分别快 23.4% 和 25.9%，带真实回复的连续对话快 9.4%。新版本串行回归未触发紧凑 KV 和同批写入。

正式候选验证共 388 次计时请求，同轮逐条比对均一致。基准使用本地 OpenAI 兼容 Chat Completions 流式入口。本机依赖缺少 OpenAI SDK 的一个可选类型，Responses 入口未启动。验证覆盖这一模型、Apple Silicon MLX 后端和所列实验负载。CUDA、多卡、其他模型及生产流量未测。

带回助手回复的对话，三轮原版和候选整批耗时分别为 1330 → 1233 ms、2549 → 6515 ms、1218 → 1098 ms。慢轮的缓存命中与输出一致，后四次请求均变慢。该轮未启用紧凑 KV 和合并写入，确切原因仍待进一步定位。

四路回放中，紧凑 KV 只在实际合并写入的批次中触发。调度状态对单请求的提示由回归检查覆盖，当前回放未测到该路径的性能。

交付版的逐请求数据位于 `results/adaptive-parallel.json`、`results/adaptive-serial.json` 和 `results/adaptive-chat-clean.json`。桌面重启中断了连续对话的一次配对。补跑原版进程后的数据与中断前的可公开遥测与逐请求数据一并保留，正式统计使用三个完整配对，包含第二轮观察到的连续对话慢尾。
